## 1. 产品层需求缺口（比代码问题更致命）

### 1.1 最大缺口：内容规模 ↔ 导航结构不兼容

现在的心智模型是「入口 → 一条卡片流 → 一直滑」。这在 8 张卡时成立，在 **530 张**时直接崩：

- 3 岁孩子没有"分类"概念，但也没有"滑 200 次"的耐心；
- 家长想找"大象"时只能从头滑到尾；
- `section`（fruits / animals / vehicles…）已经写进数据，却没有任何 UI 消费它 —— **这是文档里最明显的一处"设计意图未落地"**。

> 这一条会直接决定 UI 定型（见 §4），必须先拍板。

### 1.2 年龄分层实际只实现了 L1

- `AGE_CONFIG` 只改字号，不改内容深度；
- **故事卡 L2/L3 是空的**：`renderStageCard` 里 `lv.text || card.zh`，而 story 卡只有 `levels.L1.text`，所以 L2/L3 孩子看到的不是句子，而是"小兔子""大树爷爷"这种名词（`index.html:1150`）—— 叙事直接断掉。
- 古诗 `focusLines`（L1 只读前两句）在 Content Spec 里定义，代码零引用；`pinyinLines` 同理，古诗页根本没有拼音行。

### 1.3 时长/防沉迷是空壳

PRD 把「温柔收尾」当成核心差异化，但：
- `stats.totalSeconds` 从不累加（只在 DEFAULT_STATE 里初始化）；
- 没有 `setInterval` 计时，没有到 15 分钟自动进入晚安态；
- 晚安浮层的关闭按钮写着"**家长长按**结束并交还手机"，实际是**单击即关**（`index.html:1761`），3 岁孩子一点就出去；
- 首页还挂着一个**孩子可见的**「🌙 演示：温柔晚安仪式」按钮（`index.html:526`）。

### 1.4 家长侧能力缺失

- 亲子抽屉只能从卡片右上角 💡 进入，Design Spec 承诺的"双指上滑"没实现；
- 没有设置页：年龄档能改，但播放模式、时长、清空收藏、内容包更新都没有入口；
- 家长闸门长按 3s 只是解锁「年龄选择屏」，改完年龄没有任何二次确认。

### 1.5 商业化与合规完全没讨论

- 免费 / 内购 / 一次性买断？红线说不做诱导付费，但**收入模型空白**；
- 儿童应用商店合规（COPPA / 国内《儿童个人信息网络保护规定》）没提；
- 内容版权：古诗公有领域没问题，但 48 首的**插画、CC0 音效来源清单**必须留档；
- 应用体积红线（图片 ≤15 MB + 音频 ≤12 MB）在 App Store 蜂窝下载限制（iOS 200 MB 以内宽松，但首屏体验要求更高）下没问题，**但 1.5 MB 单文件 HTML 内联 base64 的做法必须在上架前换掉**（无法增量更新、无法缓存、首屏解析 ~200ms）。

### 1.6 文档自相矛盾清单（必须先统一，否则实现永远对不齐）

| # | 冲突点 | A 说法 | B 说法 | 建议 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 内容规模 | PRD：302 词 / 36 诗 / 12 故事 / 54 关 | Catalog：530+ / 48 / 20 / 60 | 以 Catalog 为**目标**，以 PRD 为**首发**，PRD 改为"首发版规模" |
| 2 | 插画风格 | PRD：温暖**水彩**绘本 | Pipeline：**扁平矢量** clipart + 纯白底 | 二选一（推荐扁平矢量 + 透明底，见 §5.3） |

## 3. 技术选型

### 3.1 约束条件（来自 AGENTS.md + 产品现实）

1. 3–5 岁单机离线，**无账号、无网络依赖**；
2. 内容 ~700 卡片、~800 音频、~700 图片，纯静态，需**增量更新**；
3. 音频必须毫秒级响应 + 可原子打断（当前会话号方案是对的）；
4. 手势/画布/音画同步对帧率敏感；
5. 交付形态：iPad 优先（家长最可能给的设备），Android 平板次之，桌面非必需；
6. 团队规模未知 → 优先"一个人也能维护"的技术。

### 3.2 候选对比

| 方案 | 包体 | 音频控制 | 12 种卡片类型可维护性 | 复用现有原型 | 上架成本 | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **A. 原生单文件 HTML（现状）** | 最小 | 好 | ❌ 字符串模板到 12 类会烂 | 100% | 无（只能浏览器） | 仅原型 |
| **B. Vite + TS + Vue 3 + Capacitor** | 中（~90 KB runtime） | 好 | ✅ 组件化，12 个 CardRenderer | 高（结构可平移） | 低（一套壳 iOS/Android） | **推荐** |
| **C. Vite + TS + Svelte + Capacitor** | 最小（~15 KB） | 好 | ✅ | 中 | 低 | 备选（若极致抠体积） |
| **D. Vite + TS 纯原生（无框架）+ Capacitor** | 小 | 好 | 中（需自建渲染器注册表） | 高 | 低 | 保守备选 |
| **E. React + Capacitor** | 大 | 好 | ✅ | 中 | 低 | 无必要，生态过重 |
| **F. Flutter** | 大（~25 MB） | 优秀 | ✅ | ❌ 全重写 | 中 | 若日后要桌面+移动统一再说 |
| **G. React Native** | 大 | 一般（需额外音频库） | ✅ | ❌ | 中 | 音频打断链路更麻烦 |
| **H. 纯原生 Swift/Kotlin** | 最小 | 最强 | ✅ | ❌ | 高（两套代码） | 除非要做付费精品 |

### 3.3 推荐方案（分三阶段，不破坏"原型阶段不引构建"的约定）

```
阶段 0（现在）  单文件 HTML 原型           ← 保留，用于快速发给人看
阶段 1（1~2 周） 拆分：Vite + TS + Vue3 + JSON 内容 + 资产流水线
                · 目录：src/{shell,cards,audio,state,ui}
                · 内容：content/*.json（每类一个文件）+ zod/JSON-Schema 校验
                · 资产：assets/{images,audio}/…（不再是 base64）
                · 构建产物：dist/ 纯静态
阶段 2（2~4 周） Capacitor 打包 iOS/Android + PWA 双出口
                · 存储：Capacitor Preferences（替代 localStorage）
                · 音频：Capacitor 社区 audio 或原生 AVAudioPlayer 桥（保证打断原子性）
                · 内容包：assets 按"章"分目录，支持热更新 zip 下载（可选）
```

**为什么是 Vue 而不是继续原生字符串模板**：12 种卡片类型 × 3 个年龄档 × 5 种播放态，`renderStageCard` 已经是 165 行巨型 if-else（`:1057-1221`），扩到 530 卡 + 6 类益智后不可维护。Vue 的 `v-if` + 组件注册表能把「加一类卡片」降到"新建一个组件 + 注册一行"。

**为什么是 Capacitor 而不是 Tauri**：Tauri 桌面为主，iPad/Android 平板是主战场；Capacitor 直接复用 Web 层，一套代码三端。

**音频方案要点（必须写进技术文档）**：
- 预烘焙 mp3 → 构建时转 `m4a`/`opus`，Web 用 `<audio preload="auto">` 池化复用（不要每次 `new Audio`）；
- 保留现在的"会话号作废"机制（`playSessionId`）——这是全项目最聪明的一段代码；
- iOS 首帧必须由用户手势触发 `AudioContext` 解锁，否则静音；
- **禁止**把 Web Speech 当兜底上线（PRD 已列为红线），只留 dev flag。

**内容治理（比技术栈更重要）**：
- `content/*.json` + JSON Schema，CI 里跑：id 唯一、`gestureLock` 必填、古诗 4 句 + 拼音、故事 4–5 页、每个音频/图片文件存在；
- 一条命令 `pnpm gen:assets` 从 catalog 生成待生成清单 → edge-tts / Pollinations → 写入 `assets/`。

## 4. UI 选型分析（重点）

### 4.1 五种候选架构

```
U1 · 单卡全屏流（现状）
  Home ──► [ ‹ 🔊 ▶ ❤️ › ] ──► 卡片 ──► 卡片 ──► …
  优点：极致专注、实现最简、"一页一物"最纯
  缺点：530 词无法定位；孩子只能"往下滑"；家长找不到指定内容

U2 · 分类大图标网格（图鉴目录）
  Home ──► Grid(2×3 大卡) ──► 分类内卡片流
  ┌──────┬──────┬──────┐
  │ 🍎   │ 🥕   │ 🐱   │   ← 每格 ≥ 150×150，一格一个分类
  │水果  │蔬菜  │动物  │
  ├──────┼──────┼──────┤
  │ 🚗   │ 🍰   │ 🌳   │
  └──────┴──────┴──────┘
  优点：符合实体图鉴/绘本目录直觉；点选代替滑屏；可承载 530 词
  缺点：多一层；分类名是文字（孩子不识字，必须靠图标 + 语音）

U3 · 横排书架 / 抽屉
  ─────────── 横向滑动书架 ───────────
  [水果][蔬菜][动物][交通][美食]…
  优点：探索感强、可爱
  缺点：横向滑动 + 卡片流内纵向翻页 → 两套手势冲突，3 岁难分辨

U4 · 场景探索地图
  一张果园/动物园大场景，点场景里的物体进入卡片
  优点：沉浸、惊喜
  缺点：530 词要做 530 个场景坐标，内容成本爆炸；命中率低

U5 · 横屏双栏舞台（文档已设计，代码未实现）
  ┌──────────┬──────────┐
  │  大图    │ 中文/英文 │
  └──────────┴──────────┘
  优点：iPad 横放时最佳；图与字同时可见
  缺点：需重排布局；竖屏体验无增益
```

### 4.3 推荐：U1 + U2 组合（三壳结构），U5 作为横屏变体

```

   ┌────────────────────────────┐
```

### 4.4 底栏：5 槽在数学上不成立

```
可用宽度（iPhone SE 375）：375 - 32(padding) = 343px
现状 5 槽：56+48+72+48+56 = 280 + 4×14(gap) = 336px   ← 勉强
若全部 ≥64px：64+64+80+64+64 = 336 + 4×8(gap) = 368px ← 溢出
若全部 ≥64px 且 gap 14：336+56 = 392px              ← 360px 屏直接崩
```

**解法：视觉尺寸 ≠ 触控热区**

```css
/* 视觉 48px，热区 64px —— 用伪元素扩展命中区域，不影响排版 */
.mode-btn { width:48px; height:48px; position:relative; }
.mode-btn::before { content:''; position:absolute; inset:-8px; border-radius:50%; }
```

这样既守住"3–5 岁触控 ≥64px"的生理红线，又不撑爆 360px 窄屏。**建议把这条写进 Design Spec，替换掉"48px 就是 48px"的说法。**

### 4.5 底栏的另一个真问题：4 态循环对孩子是"隐藏陷阱"

现状：🔊 → 🔁 → 👆 → 🔇 → 🔊 无限循环，全靠一个按钮 + 一个 emoji。

- 3 岁孩子无法从 🔁 与 👆 的区别理解"单卡循环"和"自由点读"；
- 每点一次就换一种行为，**同一次点击的后果不可预测** —— 这是最差的一种交互；
- 静音态下 ▶ 变成死键（§2 P0-3）。

**三个候选**：

| 方案 | 形态 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| B1 保留 4 态循环 | 现状 | 省地方 | 不可预测、静音死键 |
| **B2 精简为「声音开关」2 态** | 🔊/🔇 二值 | 孩子一眼懂；家长也懂 | 失去"单卡循环磨耳朵" |
| **B3 分离：底栏只放声音开关，高级模式进家长层** | 底栏 2 态 + 家长抽屉里选 4 种 | 孩子端极简，家长端完整 | 家长要多点两下 |

**推荐 B3**（*未采纳，决策为 B1，补偿方案见 §8.2*）：
- 孩子端底栏：`‹` `🔊/🔇` `▶/■` `❤️` `›`（5 槽保留，但模式键退化为纯声音开关，行为可预测）
- 家长层（长按闸门后）：翻页即读 / 单卡循环 / 自由点读 / 静音 + 自动巡航间隔 + 时长上限
- 这样"磨耳朵"变成家长设定的**使用场景**，而不是孩子要理解的**模式**

### 4.6 视觉语言：现在有两套互斥的定义，必须选一套

| | 方案 V1「水彩绘本」（PRD 说法） | 方案 V2「扁平矢量 clipart」（Pipeline 说法） |
| :--- | :--- | :--- |
| 观感 | 柔和、有笔触、暖、像绘本 | 干净、高饱和、粗轮廓、像闪卡 |
| 3 岁辨识度 | 中（笔触会干扰轮廓） | **高**（粗黑轮廓 = 强边界） |
| 生图可控性 | 低（AI 水彩易跑偏成油画/脏色） | **高**（prompt 稳定，`flat 2D vector` 锁死） |
| 与卡片底色融合 | 需透明底 | 若纯白底则**与暖色卡片打架**（截图已暴露） |
| 全库一致性成本 | 高 | 低 |
| 体积 | 中（WebP 有 alpha，20–35 KB） | 低 |

**推荐 V2 + 两条硬约束**（*未采纳，决策为 V1 水彩，落地约束见 §4.7*）：
1. **透明背景**（alpha WebP），彻底放弃"纯白底"，让插画直接坐在 `palette` 卡片底上 —— 这同时解决 §2 P1-13 的白框问题；
2. **粗轮廓线 ≥ 4px（800px 画布下）**，这是幼儿轮廓知觉的关键。

配套：卡片底色统一降到 `--palette` 的低饱和系（现状 `#FFF1E8` 等已经不错），插画主色饱和度拉高 → **背景柔、主体艳**，对比度天然形成。

### 4.7 水彩方案（D2）落地约束 —— 必须配套，否则会崩

水彩的天然弱点是「边缘柔 → 3 岁轮廓辨识度低」和「AI 易跑偏成油画/脏色」。不做补偿，就会得到一个漂亮但对幼儿无效的产品。五条硬约束：

**① 水彩质感 + 明确轮廓（两者兼得，不是二选一）**
```
prompt 追加：soft watercolor washes with gentle color bleed,
BUT with a clean dark ink contour line defining the silhouette
```
- 主体外轮廓保持 2–3px 深色（`#4A3F35` 系，不用纯黑）；
- **内部细节可以水彩化、可以模糊**，但**外轮廓必须清晰** —— 幼儿识别靠的是剪影形状，不是纹理。

**② 背景处理：把"白框"变成设计，而不是 bug**
水彩必然有纸底。硬抠白出 alpha 会在柔边产生杂边/灰边（更丑）。正解是**接纳纸感**：
- 插画统一生成在 `#FFFDF8` 水彩纸底上，800×800，**不做透明**；
- 卡片内给插画区一个 **`border-radius: 20px` + 内阴影 + 4px 白边**，做成"**画片 / 贴纸 / 图鉴卡片**"的实体感；
- 这样白底变成"纸"，与暖色 `palette` 底形成**两层卡片**的纵深，比透明贴图更有"图鉴"味道。

> ⚠ 关键：**所有插画的白底必须是同一个色值 `#FFFDF8`**，否则 700 张图会出 700 种白。

**③ 一致性控制（700 张同风格）**
| 手段 | 做法 |
| :--- | :--- |
| 固定 seed 池 | 每个分类锁 1 个 seed（`seed=2026` 起），同分类内差异小、跨分类有变化 |
| 风格参考图 | 先生成 1 张"黄金基准图"（如苹果），后续用 img2img / IP-Adapter 以它为 style reference |
| 负向词强制 | 必须追加 `oil painting, impasto, heavy brush strokes, muddy colors, dark shading, grunge texture, canvas texture, photorealistic, 3D render` |
| 抽样验收 | 每分类抽 3 张人工过目，不合格整批重跑（不要逐张修） |

**④ 色彩饱和度补偿**
水彩天然低饱和，而 3–5 岁视觉敏感期需要高饱和刺激。补偿：
- prompt 加 `vibrant saturated watercolor, bright cheerful palette`；
- 后期统一做一次 `saturation +15% / contrast +8%` 的批量调色（Python + Pillow 一行搞定）；
- 卡片 `palette` 底色**降低**饱和度（现状 `#FFF1E8` 系已合适），形成"底柔、主体艳"的对比。

**⑤ 尺寸与体积（水彩比扁平矢量更吃体积）**
- 800×800 WebP **quality 80**（水彩渐变多，q82+ 体积翻倍）；
- 单图目标 **35–50 KB**（比原定的 20–35 KB 放宽）；
- 全库 700 张 ≈ **28 MB** → **超出原定 ≤15 MB 红线**。必须二选一：
  - (a) 尺寸降到 640×640（屏幕够用，体积约 -36%）→ ≈ 18 MB；
  - (b) 按 Phase 分批下发内容包（首发只带 120 词 ≈ 5 MB）。
  **推荐 (b)**：首发 120 词 + 分批内容包，既守体积红线又给后续更新留出口。

### 4.8 主视觉尺寸：现在浪费了 60% 的卡片面积

```
截图实测：375 宽卡片 ≈ 343×520，apple 图 210×210
→ 图片占卡片面积 ≈ 24%，留白 ≈ 76%
```
红线是"图大、字少、留白多"，但"留白多"指的是**呼吸感**，不是"图小"。

建议：`.hero-img { max-width: min(78vw, 420px); max-height: 46vh; }`，让图随屏幕长，长边不低于卡片宽度的 70%。

**关键规则**

1. **格子 = 一张卡，不是分类**。分类只存在于顶部胶囊条。这样从 Grid 点进去**直接落 Stage 且索引正确**，无需二次选择。
2. **分区胶囊必须带图标**（孩子不识字），长按/单击时**语音报读分区名**（`"水果"`）。
3. **每屏 6 格（2×3）或 9 格（3×3）**：
   - 手机竖屏 6 格（2 列 × 3 行，格 ≥ 150px 高，图够大）
   - 平板/横屏 9 格（3 列 × 3 行）
4. **已看过的卡**给一个极淡的角标（`✓` 或灰化 20%），**不做进度百分比**（孩子不懂百分比，也避免"要刷完"的压力）。
5. **点击格子 → 进入 Stage，`currentList = 该分区全部卡片`，`currentIndex = 该格索引`**。这样孩子在 Stage 里左右滑，是在同一分区内滑，符合直觉。
6. **进 Stage 的动画必须从格子位置放大展开**（`transform-origin` 跟随格子），让孩子建立"我点的是这张"的因果感。
7. **收藏格（我的最爱）不走 Grid**，直接从 Home 点进去就是 Stage（收藏通常 <20 张）。

### 8.2 D3 · 4 态循环的可预测性补偿（保留 B1 但必须补 4 条）

既然保留 `🔊 翻页即读 → 🔁 单卡循环 → 👆 自由点读 → 🔇 静音`，就必须解决它的三个固有缺陷：

**① 静音态下 ▶ 是死键 → 改为「视觉巡航」**
```ts
// startAutoPlayCruise 内部：静音态不发声，但仍自动翻页
if (S.prefs.playMode === 'quiet_mute') {
  await safeSleep(3000, cruiseSession);   // 3s 看图时间
  stepCard(1);
  continue;
}
```
按钮永远有反馈，红线不破。

**② 同一次点击后果不可预测 → 每次切换给「图标 + 语音 + 短动画」三重确认**
- 现状只有 emoji 变化 + toast 文字（孩子不识字，等于没有反馈）；
- 改为：按钮图标放大弹一下 + **播放一句人声**（`"翻页就读书"` / `"一直读这一页"` / `"点哪里读哪里"` / `"安静看书"`）+ 图标外圈转一圈；
- 这 4 句人声需新增 4 条预烘焙音频（`mode_flip_zh` / `mode_loop_zh` / `mode_tap_zh` / `mode_mute_zh`），**这是 B1 方案的必要成本**。

**③ 🔁 与 👆 语义太近 → 图标区分度拉满**
| 模式 | 现 emoji | 建议图标 | 理由 |
| :--- | :--- | :--- | :--- |
| 翻页即读 | 🔊 | **🔊 + 翻页箭头**（或自绘 SVG） | 喇叭 + 翻页，语义最全 |
| 单卡循环 | 🔁 | **🔄 + 锁**（自绘 SVG） | "锁在这一页"比"循环箭头"更直观 |
| 自由点读 | 👆 | **👆 + 声波**（自绘 SVG） | 手指 + 发声 = 点哪读哪 |
| 静音 | 🔇 | **🔇**（保持） | 已是国际通用符号 |

> emoji 在跨端渲染差异大（Android/iOS 长得不一样），**底栏这 4 个图标建议全部自绘 SVG**，尺寸一致、可加动效、颜色可控。

**④ 家长侧的"锁定模式"**
长按闸门后可勾选「锁定当前模式」—— 防止孩子在 Stage 里乱点模式键把家长设好的"磨耳朵"改掉。这是 B1 方案的必要配套。
